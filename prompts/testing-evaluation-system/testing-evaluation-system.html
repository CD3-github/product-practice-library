ApproachQuestionExampleWhat you get
Deterministic testsDoes it meet an explicit requirement?A saved draft can be reopened with the same content; an unauthorized user cannot edit it.Pass/fail and a location to investigate.
EvalsHow well does it perform?Check whether a generated draft is accurate and useful, alongside its latency and cost.Scores or measurements with reasons and examples.

One feature can use several approaches. For an AI editor, test saving and permissions, eval draft quality, then observe real use. Add a controlled experiment when you need to attribute a change in completion to a particular design.
Where do golden sets, robustness checks, and release methods fit?
  • Golden set: a maintained set of representative cases reused to check quality or regressions.
  • Unit, integration, and E2E tests: check one component, connected components, or the full user path.
  • Robustness, load, and failure injection: vary inputs, traffic, or dependency failures to see whether behavior remains acceptable.
  • Red-team and blue-team exercises: deliberately challenge the system and assess its defenses and response.
  • A/B estimates a product change’s effect. A/A checks experiment infrastructure by giving groups the same experience.
  • Shadow runs a candidate alongside the live system without serving its result or executing external actions. Canary exposes a small traffic share first, with monitoring and rollback.

What should the agent send for human review?

Each request should include the actual output, relevant input, criterion, agent assessment, and one specific question. Prioritize borderline scores, conflicting judgments, unfamiliar failures, and serious risks; sample some passes to check for missed problems.

How the system works

Connect the parts into one repeatable loop

A case passes through the feature, its output is checked, and the result informs the next change. The seven parts below make that process consistent across versions.

Define
1 · Evaluation agreementState the decision, what good looks like, and which failures block release.
2 · Case collectionInclude typical tasks, difficult inputs, and known past failures.
Run
3 · Step interfacesRecord what each step receives and returns so failures can be traced.
4 · RunnerRun the same cases automatically and keep each input and output.
Assess
5 · GradersUse code, a model, or a person to apply the criteria consistently.
Record
6 · Run recordKeep the version, settings, results, time, and cost so others can reproduce the run.
Decide
7 · Analysis and decisionExplain the findings, request necessary human judgments, and choose the next action.
Use confirmed findings to improve the feature or the cases, then run again.
Engineering terms and where they belong
  • Eval contract: the evaluation agreement. Stage contracts: the input/output rules between steps.
  • Scenario registry: the maintained case collection, with identifiers and versions. Run manifest: the record of one run and its configuration.
  • Harness: the setup that connects cases, execution, graders, and records. A gate is a rule deciding whether a result is sufficient to proceed.
Eval matrix

Choose the cases, criteria, and way to judge

An eval matrix shows which cases are checked against which criteria. A grader supplies the actual judgment or measurement for each applicable combination.

Cases: what do we try?

For a writing feature, include a clear brief, an incomplete brief, and a brief with conflicting facts.

Criteria: what counts as good?

Check factual accuracy and usefulness separately. Define an example of a good and a poor result for each.

Graders: how do we judge?

Use code for exact requirements and calibrated model or human judgment for meaning and usefulness.

Why check the grader itself?

A model can give a fluent but incorrect answer a high score. Compare its ratings with qualified people on good, poor, and borderline examples before using the score to decide a release.

  • Give the grader the source facts it needs to judge accuracy.
  • Record reasons and examples, not only the final score.
  • Check missed serious errors and false alarms separately.
  • Recheck ratings after changing the model, instructions, or scoring criteria.
How to organize cases for ongoing improvement

Use development cases while tuning, regression cases to protect existing strengths, and calibration cases to check graders. Keep a separate held-out set for later assessment so repeated tuning does not simply memorize the examples.

Compare alternatives

Compare against what users would actually use

A baseline is the reference option. A benchmark is the comparison process. First identify a credible alternative, then give each option a fair task and consistent scoring.

A · Current approach

Observe how a user completes the task today, including preparation and editing effort.

B · Same information

Give a capable alternative the same approved source material. This helps identify the value of the specialized workflow.

C · Your feature

Run the real feature from input to final result and account for the user’s remaining work.

An example comparison design. Choose the options that answer your question. Compare output quality alongside effort, cost, and speed, using pre-agreed requirements for what improvement matters.
How to keep a comparison fair
  • Confirm the alternative’s current capability and version.
  • Keep the task, source material, deliverable, and scoring comparable. Document any deliberate differences.
  • Repeat variable runs and report the spread as well as the average.
  • Include preparation, retries, editing, and review effort in the comparison.
After release

Use real failures to improve the next check

Offline evals use a controlled case collection. Online evals inspect actual use. Connecting the two helps you catch both familiar regressions and new problems.

Offline: repeat known cases

Compare versions and safely reproduce failures with fixed inputs, without involving live users.

⇄

Online: learn from real use

Monitor errors and response time; sample outputs for quality. Turn confirmed new failures into reusable offline cases.

When do you need product analytics or an experiment?

Analytics shows whether people start, finish, or return. If completion improves after a release, other changes may also explain it. A controlled experiment helps estimate the effect of the specific change.

Implementation details

Build one useful check, then expand

The agent can carry out this sequence. At each step, the output answers a concrete question and becomes the input for the next step.

1 · Understand the feature

Inspect the actual user path, code, and existing checks. Identify the failures that would matter most to users.

  • You get: a verified gap list and a first priority.

2 · Agree on a useful check

Choose representative cases and clear success criteria. Try the scoring method on a few examples to confirm it can distinguish good and poor results.

  • You get: a small, reviewable test or eval plan.

3 · Run one complete path

Within the approved scope, connect input, feature execution, scoring, and result records. Have the agent analyze what failed and why.

  • You get: a repeatable run and an explained result.

4 · Review and improve

Review the cases needing human judgment. Add confirmed problems to future checks, compare versions, and expand coverage as risks become clear.

  • You get: a decision, next action, and cases that protect the improvement.
What the implementation needs to preserve
  • Inputs and outputs at important steps, so the first failing step can be found.
  • Case, model, prompt, code, and scoring versions, so runs remain comparable.
  • Raw results plus agent analysis; invalid runs should be distinguishable from product failures.
  • The human decision and follow-up action, linked to the evidence that supported them.
