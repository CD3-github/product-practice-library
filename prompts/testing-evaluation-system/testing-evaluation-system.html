Compose around the evidence gap.

A prompt revision may need only offline eval; a permission change may mainly need tests; an AI workflow may combine contract tests, output eval, and production validation. A shared harness should preserve the meaning of rule failures, weak quality, invalid runs, and insufficient evidence.

Combine rule checks, quality judgments and repeated runs

Tests and evals can use the same cases. Build the combination by choosing how to judge each requirement, then deciding whether repeated runs are needed to understand variability.

  • Check directly verifiable rules. Use deterministic checks for required fields, value limits or permission rules. With a fixed rule, the same recorded input and output produce the same verdict.
  • Judge contextual quality. Define clear criteria for qualities such as relevance and usefulness, then use qualified human review or a validated model judge to assess them.
  • Measure variation when it matters. When the same task produces varying results, repeat it as needed and apply the selected checks to each result. Use success rates or score distributions, with uncertainty, to assess how reliably the system meets the criteria.

Cases, criteria and judgment

Define the inputs and conditions, the expected behavior, and how each result will be judged. Together, these make the selected verification approach executable.

Scenario axes

Which variations should cases cover?

The same feature may behave differently across users, inputs, permissions, and operating conditions. Use axes to choose cases systematically.

Criteria

What counts as good?

Define invariants, quality dimensions, scoring anchors, thresholds, operating limits, and capabilities to protect.

Graders

How will results be judged?

Use code for exact rules and validated model or human judgment for contextual quality. Keep evidence and uncertainty with the score.

Scenario axes · selection questions and examples

Select the axes that materially change performance or risk. Input completeness and context consistency are separate axes: a complete brief can still contain conflicting facts.

Coverage dimensionWhat to considerExamples
User and domainDo requirements change across users or domains?New and experienced users; different professional domains.
Goal and lifecycleWhat is the task, and where is the user in it?First creation, editing existing content, retry, or recovery.
Input variabilityWhich supported representations or information gaps could change the result?Equivalent facts in supported formats or media; missing fields; damaged or unsupported input.
Contextual complexityWhich intents and facts remain active across evidence, corrections and history?Competing intents, ambiguous tool fields, stale evidence, or a corrected fact in a long conversation.
Risk and authorityWhat are the consequences of error, and what actions are allowed?Read-only advice, editing access, or approval required before execution.
Tool or provider stateHow does the feature behave when dependencies change?Normal, timeout, rate limit, or partial results.
Scale and loadDoes input size or workload change performance?Large inputs, concurrent requests, or batch tasks.
Personalization and customizationWhat may adapt, and which requirements remain protected?A requested writing style or output shape; conflicting instructions; saved preference changes only if persistence exists.

Prioritize frequent tasks, high-risk cases, and known failures. Add important combinations, such as sparse input plus authority to execute. Choose combinations by risk rather than enumerating every permutation.

For selected variations, specify the original conditions, what changes, expected behavior and how to observe it. Include normal cases; add combinations only when they reflect a real risk.

Check whether behavior should stay stable, adapt, ask for clarification or follow a safe fallback. A formatting option does not imply memory, tool or multi-agent coverage.

Dataset partitions · development, regression, calibration, and held-out

Separate cases by their purpose and record any overlap. Repeatedly tuning against the final assessment cases makes the result less informative about unseen work.

PartitionUse
Development setTune the implementation, prompts, and rubric.
Regression setCheck that known capabilities and previous fixes still hold.
Calibration setCheck grader reliability against reviewed judgments.
Held-out setAssess performance on cases not used during tuning.

Choose and combine evaluators

Choose what to assess and how to judge it separately. Code, people and models can return labels or numbers: a human can rate usefulness from 1–5, and a model can return pass/fail. Quantitative results do not by themselves establish deterministic or valid judgment.

MechanismUse it forCheck its limits
Code checks and metricsRule and state assertions; defined quantities such as error rate, latency and costCheck the oracle, formula, units and denominator; runtime measurements vary, and structural validity does not establish quality
Human evalDomain usefulness, ambiguous cases and calibration labelsRelevant expertise, evidence, anchors and how disagreements are resolved
LLM-as-a-judgeRepeated contextual assessments against a clear rubricAgreement with qualified human review, order/length bias and invalid judge responses

Combine mechanisms for distinct responsibilities: code checks output structure, then a person or validated judge checks meaning and usefulness. Keep mandatory failures separate from quality scores; unresolved grading is not a product pass or fail.

Grader validity · check scoring before using it for decisions

A grader can reward a fluent but incorrect answer. Check it on strong, weak, borderline, and serious-failure cases before using its scores for release decisions.

  • Provide the source facts and context needed to judge each criterion.
  • Define concrete scoring anchors; keep reasons tied to observable evidence.
  • Compare with qualified human ratings using defined agreement or error measures. Inspect missed serious failures and false alarms; use independent confirmation when needed after tuning.
  • Blind candidate identity where practical to reduce preference bias.
  • Version the model, instructions, rubric, context, and parser. Revalidate after material changes and define how disputes are adjudicated.
Eval matrix · connect cases to criteria

Use a matrix to connect cases, applicable criteria and graders. First define each case's expected behavior: produce, clarify, decline or recover. A correct decline may pass without generated content to score. Keep expectations, measured results and unmeasured cells distinct.

Grader design →

Method designs · open what you need

TestCheck specified behavior at the relevant boundary.
Question

Does the required behavior hold, including consequential failure paths?

Design

Choose the function, contract, service or end-to-end boundary. Set input and initial state, trigger the action, then assert the expected return, saved state or side effect. Use isolated fixtures for risky operations.

Read the result

Inspect failed assertions and the first divergence. Distinguish product defects from broken fixtures or environments; use passing checks only for the boundary they exercise.

Avoid misreading

A helper test or valid intermediate object does not establish consumer read-back. Exact text equality is unsuitable when several outputs are valid.

Detailed workflow reference →
EvalAssess task performance against explicit criteria.
Question

How well does the system meet the intended task and quality requirements?

Design

Select representative cases and material edge cases. Define anchors and acceptance before the run; choose code, human or validated model grading by criterion. Repeat stochastic runs when the decision needs an estimate of variation.

Read the result

Report applicable criterion results, hard failures, weak segments and uncertainty. Keep missing evidence visible and use held-out cases for claims about unseen work.

Avoid misreading

A high average can hide a critical failure. A numerical judge score is not automatically objective, and an offline score does not establish business impact.

Detailed workflow reference →
BenchmarkChoose the comparison that answers the decision.
Question

Is a version better, is the product worth using, or does one component contribute?

Design

Research credible alternatives and their current capabilities before choosing a baseline. Compare a change with the current version, product value with a realistic alternative such as a manual process or general-purpose AI, and component contribution with a controlled ablation. Use matched tasks and shared criteria; document information access, versions, settings and user effort.

Read the result

Compare quality, protected capabilities, cost and user effort against pre-agreed meaningful differences. Tie conclusions to what differs between arms: checking an unchanged component for regression does not establish its superiority. Report uncertainty before choosing whether to adopt, iterate or retain the baseline.

Avoid misreading

A weak comparator inflates value. Equal-information and natural-use comparisons answer different questions; a whole-product comparison cannot isolate one component. Relative preference alone does not prove either option is acceptable.

Detailed workflow reference →
Production validationCheck whether real use matches the supported claims.
Question

Does quality and reliability hold for real users, inputs and dependencies?

Design

Choose sampled online eval, monitoring or an authorized shadow/canary rollout for the uncertainty. Define segments, observation window, quality criteria, alerts and rollback rules; isolate shadow side effects and protect user data.

Read the result

Compare errors, latency and sampled task quality with agreed limits. Inspect weak segments and unexpected failures; decide to continue, repair or roll back, and turn verified failures into reusable cases.

Avoid misreading

A quiet dashboard can mean missing instrumentation. A small rollout does not establish all-user readiness, and metric movement alone does not prove causality.

Detailed workflow reference →
Controlled experimentEstimate whether a change caused an outcome.
Question

Did the intervention improve an outcome, rather than merely coincide with it?

Design

Define hypothesis, treatment, assignment unit, exposure and primary/guardrail metrics. Randomize where feasible; plan sample size, duration and stopping/analysis rules, checking interference and measurement quality. Use the analytics workflow for detailed design.

Read the result

Report effect size and uncertainty, metric guardrails, valid exposure and which population the estimate applies to. Assess practical value as well as statistical evidence.

Avoid misreading

Before/after movement or a canary is not automatically a randomized experiment. Repeated peeking or changing metrics after seeing results can invalidate the conclusion.

Set up and use

From an evidence plan to ongoing use

Start where your system is today: design the checks, connect a runnable path, or analyze an existing run. Ask your agent to follow the matching workflow within the agreed permissions; production validation continues the same cycle after release.

Define scope→Connect checks→Analyze and review→Learn from real use
1

1 · Define the decision and scope

Choose the version or task scope and the evidence sufficient for this decision.

Output: A bounded round: scope, checks, acceptance, stopping rules and deferred work.

Design a plan →Review existing coverage →
Actions and checkpoints
  • Choose the scope from the decision and current product version. Reuse sound cases, runners and results; identify what needs adapting or adding. Keep inspected facts and design assumptions distinct.
  • Select tests and evals for the actual risks. Link each check to its decision and prerequisites, so independent work can proceed while a specific dependency is resolved. Preserve required safety checks.
  • For a comparison, establish a credible baseline: what users do today or which viable alternative they could use.
  • Set acceptance and stopping rules before the run. Separate setup, automated workload and human review estimates; defer non-critical expansion with clear triggers. A budget stop preserves partial evidence, not a pass.
2

2 · Connect and verify one runnable path

Reuse existing infrastructure; add only what the agreed plan needs.

Output: A repeatable run with reliable grading and traceable records.

Set up the agreed checks →
Actions and checkpoints
  • Prepare versioned cases and suitable partitions. Choose code, qualified human review or a validated model judge for each criterion. Record which criteria, tasks and decision uses the judge's validation covers.
  • Connect selected stage contracts, runner, graders, saved artifacts, and replay. Start with a narrow path whose results you can inspect end to end.
  • Agree permissions, budgets, external effects, and timeouts. Mark incomplete or broken measurement runs as invalid so they cannot be mistaken for product results.
3

3 · Run, analyze, and decide

Let the agent run authorized checks and analyze the results first. Use its decision overview to focus human review on quality judgments, business trade-offs, and actions requiring approval.

Output: A supported recommendation, focused review list, and next action.

Run or analyze a round →
Actions and checkpoints
  • Run authorized checks or analyze saved results. Preserve original outputs, compare meaningful segments, and locate the first point where behavior diverges.
  • Separate product failures from invalid measurements. Report uncertainty and protected regressions alongside quality, cost, latency, and user effort.
  • For each human-review request, include the actual output, relevant input, criterion, agent assessment, and one specific question. Prioritize serious risks, borderline scores, grader disagreements, and unfamiliar failures; sample some passes to check for missed problems. Record the decision and its scope.

Read the results for your decision

  • Product · Connect results to user impact; choose the next product change.
  • Engineering · Check reproducibility and locate the first failure; fix its cause within the agreed scope.
  • Quality & operations · Review ambiguous or risky outputs against real workflow needs; decide whether they are ready for use.
4

4 · Validate real use and improve coverage

After an approved rollout, check whether real-user tasks maintain the expected quality and reliability.

Output: A rollout decision and reusable cases for the next version.

Analyze the evidence →Analytics and experiments →
Actions and checkpoints
  • Monitor errors and latency; sample real outputs against the agreed quality criteria. Review weak user segments and tasks instead of relying only on an overall average.
  • Use shadow or canary exposure where appropriate and authorized. Set alert and rollback conditions before exposure; isolate side effects in shadow runs.
  • After review and de-identification, turn a real failure into an offline case with an expected result. Fix the issue, rerun relevant cases, and keep independent holdouts for future validation.
  • To understand adoption, completion, or retention, use product analytics. To estimate whether a particular change caused an improvement, use an appropriately designed controlled experiment.
