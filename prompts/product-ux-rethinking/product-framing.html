Define the problem and outcome

Start with the job people need to complete and their current alternative. A feature idea becomes a product direction only when its value, responsibility, and evidence are clear.

  1. User jobTrigger, context, current workaround.
  2. OutcomeObservable completion and quality.
  3. Product modelObjects, responsibility, lifecycle.
  4. Useful MVPA bounded value hypothesis to test.
DefineWhy it mattersWhat to write
Problem evidenceShows whom the problem affects and why it is worth solving.Users, context, frequency/severity evidence, alternatives, open assumptions.
SuccessMakes a direction testable.Completed user job, quality bar, user effort, operating limits.
BoundaryClarifies what the first version is responsible for.Core job, adjacent products, required safety, future capabilities.
When evidence is weak

State a working hypothesis and the check that could disprove it. Explore concepts as proposals, then test the most consequential assumption before investing in implementation. Existing prototype code is feasibility evidence.

Compare product concepts

Compare how the product creates value and allocates responsibility. Use the same user job and quality bar for each concept.

Concept directionInteraction and responsibilityEvidence needed
Assisted workspaceThe user creates and edits with context-aware help.Does assistance reduce effort while preserving useful control?
Review queueThe system prepares candidates; the user focuses on exceptions and approval.Are drafts reliable enough, and can reviewers detect consequential errors?
Bounded automationThe system executes eligible low-risk work within explicit authority.Are permission, readiness, quality, recovery, and oversight sufficient?
Illustrative models

These are examples of structurally different approaches, not a required roadmap. Include the current manual or non-AI alternative; recommend the concept that best fits the task, maturity, and evidence.

Concept comparison checklist
  • Define the mental model, core objects, entry point, primary flow, and completion state.
  • Compare user effort, output quality, trust, authority, recovery, feasibility, and operating cost.
  • Name the highest-risk assumption and what evidence would favor or reject each concept.
  • Produce mockup variations only when interaction or information architecture remains meaningfully unresolved.

Allocate system and human responsibility

A product model explains what the system resolves, what it recommends, and which consequential decisions remain with people.

ResponsibilitySystem roleHuman boundary
Context and understandingGather permitted sources; check scope, freshness, gaps, and conflicts.Confirm goals, preferences, and material unknowns.
Generate and recommendProduce grounded candidates, validate rules, and explain trade-offs.Choose consequential trade-offs and correct unsupported assumptions.
ExecuteAct only within explicit permission and verified readiness.Approve material actions and control overrides.
RecoverRetry safely, reconcile ambiguous outcomes, and preserve progress.Choose alternatives when recovery changes the intended outcome.
AI capability specification
  • Required context, provenance, tenant scope, freshness, and memory ownership.
  • Model/tool capability, uncertainty, output contract, and deterministic validation.
  • Draft, recommendation, approval, execution, and read-back as distinct states.
  • Quality and safety evidence required before expanding autonomy.

Write the lifecycle before the screens

Name the objects and states that persist across visits. Walk through a realistic task, including waiting, leaving, returning, and recovery.

  1. UnderstandSources and goal are available.
  2. PrepareA versioned result can be reviewed.
  3. DecideAuthority and consequences are clear.
  4. Act and verifyPersist or execute; confirm actual state.

QuestionRequired answer
What does the user see and decide?Task, primary message, action, supporting evidence, advanced details.
What does the system resolve?Inputs, source of truth, validation, permission, and state change.
How does recovery work?Empty, stale, partial, failed, duplicate, interrupted, or ambiguous cases.

Scope the first useful version

Separate the user promise from its implementation dependencies. Keep the smallest end-to-end scope that can deliver the outcome safely.

HorizonProduct and designEngineering and evidence
V1 · Useful and safeCore task, decision ownership, necessary states, clear content, recovery.Real contracts/data, critical validation, bounded execution, one verified slice.
Next · Evidence-led expansionAdvanced controls, additional tasks, personalization where justified.Scale, deeper integration, automation, and optimization after gates pass.
